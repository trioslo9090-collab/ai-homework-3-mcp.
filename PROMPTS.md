\## Часть 2. MCP-сервер для анализа падений



```

Создай MCP-сервер для анализа падений тестов. Код помести в отдельную папку mcp-server/ с собственным package.json, на TypeScript или JavaScript, используя официальный SDK @modelcontextprotocol/sdk (транспорт stdio). Код приложения в src/ не меняй.

Инструменты:

1\. list\_containers — список запущенных Docker-контейнеров (имя, статус, порты).

2\. get\_container\_logs(container, tail=100) — вывод docker logs контейнера.

3\. read\_app\_log(container="auth-service", tail=100, filter опционально) — читает файл /app/logs/app.log внутри контейнера (через docker exec), с возможностью отфильтровать строки, например по level=error или statusCode 500. Важно: основные логи запросов приложение пишет именно в этот файл, а не в docker logs.

4\. query\_database(sql) — выполняет SQL-запрос к SQLite-базе приложения и возвращает результат. Разрешай только чтение (SELECT, PRAGMA), остальные запросы отклоняй с понятной ошибкой. Сначала посмотри docker-compose.yml и выбери надёжный способ доступа к базе на Windows (например, через docker exec внутри контейнера); избегай нативных модулей, которые требуют компиляции.

Для каждого инструмента напиши подробное описание: что он делает и когда его полезно использовать при расследовании падения теста.

Затем подключи сервер к Claude Code на уровне проекта через файл .mcp.json, проверь вручную, что каждый инструмент работает (например, запросом SELECT id, email, status FROM users), и объясни по-русски, как всё устроено и как мне проверить подключение.

```



\### Ревью и исправления сгенерированного кода



Версия SDK (ИИ предложил устаревшую 0.7.0):



```

Не используй старую версию SDK 0.7. Сначала проверь актуальную версию командой npm view @modelcontextprotocol/sdk version и укажи её. Пиши код под API этой актуальной версии.

```



Настройки TypeScript:



```

Используй "module": "Node16" и "moduleResolution": "Node16" — иначе импорты из актуального @modelcontextprotocol/sdk не найдутся.

```



Первая версия index.ts (старый API, exec через shell, sqlite3 CLI, слабая защита read-only):



```

Перепиши index.ts с учётом замечаний:

1\. Используй высокоуровневый API SDK 1.x: McpServer из '@modelcontextprotocol/sdk/server/mcp.js' и регистрацию инструментов через server.registerTool со схемами параметров на zod (добавь zod в зависимости). Низкоуровневый Server с ListToolsRequest/CallToolRequest в таком виде не скомпилируется.

2\. Вместо exec со строкой используй execFile с массивом аргументов (без shell): на Windows exec идёт через cmd.exe и ломает кавычки, а также это защищает от инъекций через параметры container и filter.

3\. Сначала проверь, есть ли в контейнере sqlite3 CLI (docker exec auth-service which sqlite3). Если нет — не устанавливай его в контейнер, а выполняй запрос через node внутри контейнера (docker exec -w /app ... node -e ...) с тем драйвером SQLite, который уже использует приложение, открывая базу в режиме только для чтения.

4\. Только чтение: разрешай один оператор SELECT/PRAGMA (отклоняй запросы с ";" посередине) и открывай базу в read-only режиме, чтобы "SELECT 1; DELETE FROM users" не прошёл.

Остальное (4 инструмента, подробные описания) оставь как есть. После этого собери проект (npm install, npm run build) и проверь каждый инструмент вручную.

```



Вторая версия (неверная сигнатура registerTool, формат ответа, SQL-инъекция в код node -e):



```

Почти хорошо, но исправь три вещи:

1\. Сигнатура registerTool в SDK 1.x: server.registerTool('имя', { description, inputSchema: { поле: z.string(), ... } }, handler) — имя первым аргументом, inputSchema как простой объект полей zod, а не z.object(...).

2\. Обработчики должны возвращать { content: \[{ type: 'text', text: ... }] }, а не строку.

3\. Безопасность: не вставляй SQL внутрь кода node -e (через ${} в шаблонной строке можно выполнить произвольный JS). Передавай SQL отдельным аргументом: execFile('docker', \['exec','-w','/app',container,'node','-e',script,sql]) и читай его в скрипте из process.argv\[1].

Также сделай описания инструментов подробнее: когда их использовать при расследовании (например, read\_app\_log — первым делом при 500 и неожиданных кодах ответа; query\_database — проверить существование и статус пользователя).

После этого npm install, npm run build и проверка каждого инструмента.

```
